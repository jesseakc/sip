# SMRT Maintenance Logs — SIP test fixture

A prepared, loadable test corpus for SIP, built from real maintenance text.

## Source

| | |
|---|---|
| Dataset | [`ASNIJKDNI/SMRT-Maintenance-Logs`](https://huggingface.co/datasets/ASNIJKDNI/SMRT-Maintenance-Logs) |
| Rows | 10,785 (9,706 train / 1,079 test) |
| Raw size | 2.4 MB parquet (`raw/train.parquet`, `raw/test.parquet`) |
| Licence | MIT, as declared on the Hub — see `raw/SOURCE_README.md` |
| Description | The dataset card states: *"These are just over 10,000 rows of maintenance logs and the associated train component that was replaced or fixed from SMRT Trains."* |

**Provenance caveat.** The Hub upload is anonymous (`ASNIJKDNI`) and carries no
citation, no DOI and no publisher statement beyond the one line quoted above. The
text itself is unambiguously real operational writing about SMRT Trains rolling
stock — car numbers, component names, technician names, part serial numbers and
explicit dates all appear inline. But the dataset's *chain of custody* is
unverified. Treat it as a realistic-looking corpus suitable for exercising SIP,
not as an auditable historical record, and do not publish derived claims about
SMRT from it.

## Why this dataset

SIP needs free text to be worth testing. Sensor datasets (AI4I, CMAPSS, SCANIA)
are plentiful on the Hub but numeric only — they exercise nothing in SIPmem,
pgvector, the retrieval router or the citation/verification path. This dataset is
the opposite: every row is a technician's narrative.

```
[report] TIMS showed intermittent BCU brake fault at car 2530. Train performance - ok.
~~~~~
[detail] 2530 TIMS showed intermittent BCU brake fault. Train performance - ok.
         2530 BCU Fault. Replaced 2530 ACU. Function check-OK. No leak found.
         Brake operation-OK. Old s/n: 1037/055 New s/n: 1037/048 Farid/Haiqal/Koon 44530
```

Each row is tagged with one of **766 component categories** (`BCU`, `Air Dryer`,
`Traction Motor`, `Door Operator`, `Saloon Light`, …) — the component that was
replaced or fixed. That single label is what makes the mapping onto SIP's domain
model possible.

## What the fixture contains

| SIP object | Count | Derived from |
|---|---|---|
| `location` | 7 | One site + one group per car-number series |
| `asset_type` | 1 | Train Car, with a JSON Schema for its custom attributes |
| `asset` | 585 | One per distinct car number appearing in the logs |
| `part` | 766 | One per component category |
| `work_order` | 10,785 | One per log entry, with narrative + resolution + part usage |

Asset status is `degraded` for a car whose most recent log defers work
("raise to RSW", "to monitor", "pending") and `operational` otherwise, because
every other log in the corpus ends with the repair completed and function-checked.

## Layout

```
data/smrt-maintenance-logs/
├── README.md                      this file
├── raw/                           downloaded source, kept verbatim and committed
│   ├── train.parquet  test.parquet
│   ├── label_names.json           the 766 component categories
│   └── SOURCE_README.md           the dataset card as published on the Hub
├── scripts/
│   ├── analyze.py                 exploratory profiling of the source
│   ├── build_fixture.py           source -> SIP canonical records
│   └── validate_fixture.py        validates output against SIP's own Rust DTOs
└── fixture/                       generated by build_fixture.py (not committed)
    ├── manifest.json              counts, load order, checksums, inferences
    ├── canonical/                 canonical JSON (load via the migration API)
    │   ├── 01-locations.json 02-asset-types.json 03-assets.json
    │   ├── 04-parts.json 05-work-orders.json
    │   └── sample-500/            a 500-row subset for quick smoke loads
    └── csv/                       the same data as flat CSV for the upload wizard
```

**The raw source is committed; `fixture/` is not.** Everything under `fixture/` is
reproducible in one command from `raw/`, and it is large (about 11 MB of canonical
JSON plus 6 MB of CSV). Run the builder before loading. The built plugin
`sip-test-bench` bundles a copy of the fixture into its `dist/` so a plain clone
has a working test bench without running Python.

## Reproducing

```bash
python3 -m venv ~/.venvs/sip-data
~/.venvs/sip-data/bin/pip install pyarrow pandas

cd data/smrt-maintenance-logs
~/.venvs/sip-data/bin/python scripts/analyze.py          # profile the source
~/.venvs/sip-data/bin/python scripts/build_fixture.py    # regenerate fixture/
~/.venvs/sip-data/bin/python scripts/validate_fixture.py # must print 0 errors
```

`validate_fixture.py` parses the canonical DTO structs straight out of
`crates/sip-domain/src/entity/migration.rs` rather than hardcoding the contract,
so it fails if the Rust definitions and the fixture ever drift apart. It checks
254,463 properties: unknown fields, missing required fields, enum values accepted
by `validate_job()`, ISO date formats, duplicate external IDs and every
cross-reference (asset type, location, parent, asset, part).

## Loading into SIP

**Dependency order matters.** The importer resolves relationships through the
migration external-ID map, so each object must exist before anything that points
at it:

```
location -> asset_type -> asset -> part -> work_order
```

Upload records with the canonical field names and add two transport keys to each
record — `external_id` and `source_object_type`. Do **not** create field mappings:
a migration job with no mappings treats each record as already canonical.

```bash
BASE=http://localhost:8000/api/v1
TOKEN=$(curl -s $BASE/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"admin@acme.local","password":"password"}' | jq -r .data.token)

# repeat per file, in order
JOB=$(curl -s $BASE/migrations -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"name":"SMRT locations","source_system":"smrt","source_object_type":"location"}' \
  | jq -r .data.id)

jq -c --arg t location '{records: [.records[] | . + {external_id: .external_id, source_object_type: $t}]}' \
  data/smrt-maintenance-logs/fixture/canonical/01-locations.json > /tmp/recs.json

curl -s $BASE/migrations/$JOB/source-records -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d @/tmp/recs.json

for step in validate dry-run import; do
  curl -s -X POST $BASE/migrations/$JOB/$step -H "Authorization: Bearer $TOKEN"
done

curl -s $BASE/migrations/$JOB/report -H "Authorization: Bearer $TOKEN"
```

The **SIP Test Bench** plugin automates exactly this, in order, with per-object
progress and rollback — see `plugins/sip-test-bench/`.

## Values that are inferred, not present in the source

The source is two columns of text. Everything structural is derived. Each
inference is recorded in `fixture/manifest.json` and repeated here:

| Field | How it is derived |
|---|---|
| Car number | First non-year 4-digit token in the log text. 96% of rows yield one. |
| Car series (`1xxx`…`7xxx`) | Grouping by the leading digit of the car number. The source records no depot, line or fleet class — this is a numeric grouping, labelled as such everywhere it appears. |
| Date | Explicit `dd.mm.yy[yy]` / `dd/mm/yyyy` where present (67%). Otherwise a trailing 5-digit code is read as an Excel date serial (28%). 4.6% of rows carry no date and are left undated. |
| Priority | Keyword heuristic: urgency terms (`emergency`, `unsafe`, `critical`) → `critical`; safety-relevant components (`brake`, `door`, `smoke detector`, `fire`, `gangway`) → `high`; recurrence thresholds → `high`/`medium`; otherwise `low`. |
| Work order type | `corrective`, unless the text reads as a routine clean/check/servicing task, in which case `preventive`. |
| Part quantity on hand | `0`. The source has no inventory data at all. |
| Part usage quantity | `1` per work order — the log records a component being replaced or serviced, not a count. |

**Nothing is fabricated.** No manufacturer, asset model, OEM, part cost, labour
hour or depot is invented, because the source carries none of them. Fields SIP
supports but this corpus cannot populate are simply left empty.

### The Excel-serial date inference is checked

'Trailing `45382`' is only a date if it is an Excel serial. That is testable, and
`validate_fixture.py` tests it: among the 368 rows that carry **both** an explicit
`dd.mm.yy` date and a trailing 5-digit code, 93.8% of the pairs land within 31
days of each other and the median absolute difference is **1 day**. The inference
holds. Rows are still left undated when neither signal is present.
