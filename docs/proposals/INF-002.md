# INF-002: Replaceable component identity and lifecycle history

Status: implementation proposal, not implemented
Priority: P0
Owner: SIP Core / SIPmem platform

## Outcome
Track physical equipment and replaceable components across installations, swaps, serial changes and service events while retaining complete history.

## Expected code surfaces
crates/sip-domain, crates/sip-assets, crates/sip-parts, crates/sip-work-orders, crates/sip-application, crates/sip-infrastructure, crates/sip-api, migrations/, tests/

## Implementation specification
### Data model
- Separate asset instance, equipment model, component slot, and installed component identity. Reuse existing asset/part/manufacturer/model entities where possible; inspect current schema first to avoid duplication.
- Slot identity is stable on host asset (e.g., rack 12 / server 4 / GPU slot 2). Physical replaceable unit has its own serial and identity independent of slot; one installed unit per slot at a time.
- Record effective-dated install/remove/replace events with actor, reason, work_order_id, old/new component, condition, warranty, provenance and audit activity.
- Add optional manufacturer part number, firmware revision, model revision and warranty metadata with explicit source provenance; avoid encoding everything as unvalidated JSON.
### Invariants and operations
- Transactional swap API: remove prior assignment, install replacement, write lifecycle event and optional work-order linkage atomically.
- Reject concurrent double-installation of the same physical component and overlapping slot occupancy; enforce via DB constraints/locking, not just UI.
- Support unknown serial numbers, temporary spares and historical imports without inventing identifiers; use internal UUIDs.
- Maintain inventory stock semantics: do not decrement stock when importing historical usage. Integration with inventory plugin is event-driven/optional.
### Acceptance
- End-to-end: failed GPU swapped into new server, old GPU retained with full service history; slot shows current occupant and time history.
- RLS, optimistic concurrency, tenant isolation, event ordering, archive/retirement, import idempotency tests.
- API schemas, migration/backfill, docs and representative fixtures.
