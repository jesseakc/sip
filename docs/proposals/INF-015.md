# INF-015: Data provenance, quality and desired-versus-observed state

Status: draft implementation proposal, not implemented
Priority: P0
Area: Shared SIP Core + optional SIP Infrastructure plugin

## Objective
Build a shared data quality and provenance layer that preserves conflicting equipment facts, observation freshness and authoritative decisions.

## Data contracts
- Represent facts/observations with entity, field, typed value + unit, source ID, observed_at, ingested_at, confidence, verification status, source revision, retention/classification and tenant.
- Model desired, observed and reconciled values separately; never overwrite source observations when authoritative values change. Historical facts remain queryable.
- Define field-level precedence policies with explicit scope (tenant, asset type, field), review-required changes, and clear handling of missing/stale/conflicting sources.
- Support manual technician assertions, manufacturer documents, imports and Redfish; AI-generated statements remain non-authoritative unless verified and approved.
## Workflow and UX
- Conflict inbox, source lineage, stale data badges, review/approve/reject/override with actor, reason and audit trail.
- Explain why a reconciled value was chosen; allow customers to change precedence without rewriting raw evidence.
- Validation for units, serial formats, timestamps, range bounds and contradictory states; avoid treating unknown as healthy.
## API and tests
- Query current authoritative value, all observations, confidence/freshness and decision trail. Emit durable change events for SIPmem indexing and downstream incident suggestions.
- E2E: manual firmware 2.1, Redfish 2.3, work-order 2.2; show three sources and choose an authoritative version through policy or human review, with no lost evidence.
- Multi-tenant RLS, RBAC, time skew, conflicting writes, late arrivals, deletion/retention, sensitive diagnostics redaction, AI-off mode.
## Dependencies
Core shared capability; integrate with INF-003 document provenance, INF-004 evidence, INF-009 discovery and INF-013 reconciliation.

## Definition of done
- Inspect latest main and overlapping PRs before implementation.
- Implement real backend, migrations, API and UI where applicable; avoid duplicate asset or document stores.
- Prove RLS/RBAC, tenant isolation, audit, idempotency, and backward compatibility.
- Automated unit, integration and end-to-end tests pass, docs/OpenAPI updated, CI green.
- Independent Repogan review and human approval before merging to main.
- Never commit secrets, PII, real facility credentials or customer data.
